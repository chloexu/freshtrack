## Problem Statement

Food waste and money waste from forgetting what's in the fridge. User buys groceries,
forgets about them, they go bad, get thrown out. The pain is real and repeating.

Every existing food tracking app has the same fatal flaw: manual entry. Adding items
one by one (barcode scanning or typing) creates enough friction that users abandon the
app within days. The insight here is to capture all grocery data at the natural
lowest-friction moment — checkout — via a single photo.

## What Makes This Cool

The checkout photo as the onboarding moment. You're already at the store with your
cart or receipt in front of you. One photo, LLM vision parses everything, predicted
expiry dates pre-filled, user just confirms. Zero manual entry.

The second unlock: LLM-parsed reminder preferences. Instead of a settings screen,
you type "remind me about fruit 2 hours after lunch" in plain English, and the app
produces a structured reminder. You tweak the cadence (daily / every 2 days / weekly)
per reminder. The app then nudges you at exactly the right moment with what you
actually have.

The real product is time-aware and behavior-aware nudging, not inventory management.
The fridge tracker is the data layer.

## Constraints

- Building for personal use first (self is the primary user)
- No backend, no auth — local-first for simplicity and speed
- Mobile-first (photos at store, notifications to phone)
- GPT-4o vision for parsing; acceptable accuracy level is "good enough for personal use"
- No recipe suggestions in v1 (distraction from the core loop)

## Premises

1. The #1 reason food tracking apps fail is activation friction — manual entry kills
   retention before the app can deliver value.
2. A receipt or cart photo at checkout is the lowest-friction onboarding moment. LLM
   vision is accurate enough for personal use (doesn't need to be 100%).
3. Meal-time reminders ("what can I eat now?") are more actionable than expiry alerts
   ("this expires in 3 days"). People act on immediacy, not warnings.
4. Mobile-first: camera at the store, push notifications to the phone.
5. LLM-parsed reminder preferences are better UX than a complex settings screen.

## Recommended Approach

**Approach C — Turbo Local-First.**

Tech stack:
- **Expo** (React Native) — cross-platform mobile, camera access, push notifications
- **Expo SQLite** — local storage, no backend needed
- **Expo Notifications** — scheduled push notifications, works without a server
- **expo-image-manipulator** — resize receipt photos before API call
- **expo-secure-store** — encrypted storage for the OpenAI API key
- **Expo AppState + BackgroundFetch** — reschedules notifications on foreground (primary)
  and nightly best-effort (secondary); see notification architecture below
- **OpenAI GPT-4o** — vision for receipt parsing, chat for reminder parsing
- **fuse.js** — fuzzy string matching for duplicate item detection

Four screens (three primary + Settings):

**0. First-launch onboarding (modal, not a tab)**

Shown once on first open. Two steps:
1. API key entry: text field + "Save securely" button. Skipping is not allowed — the
   app cannot function without it. Show a brief explanation: "Your key is stored
   encrypted on this device only."
2. Anchor time setup: two time pickers ("When do you usually eat lunch?" /
   "When do you usually eat dinner?"). Defaults: 12:00 / 18:30. Writes to `settings`
   table. User must complete this before any reminder can be scheduled.

After both steps, drop the user onto the Fridge tab. Settings tab lets them update
either value any time later.

Three primary screens, in build order:

**1. Camera / Add screen**

Input: receipt photo (v1) or cart photo (v2 — harder, lower accuracy, defer).
Receipt is structured text; cart is a 3D scene with occlusion. V1 uses receipt only.

Flow: tap camera → capture receipt → resize to 1024px max (expo-image-manipulator) →
base64 encode → GPT-4o vision call with schema prompt → parse JSON response → show
confirmation list (each item: name, quantity, freshness estimate, confidence badge for
low-confidence items in amber) → user confirms/edits → "Save to Fridge" → write to
SQLite items table → trigger notification reschedule.

Error handling: API failure or malformed JSON → "couldn't parse — add manually" fallback
(simple text form, one item at a time). Retry button on timeout. 429 → toast message.

**2. Fridge home screen**

Query SQLite for `consumed = 0` items. Derive freshness bucket from `predicted_expiry`:
- Red "Use today": expires within 1 day
- Yellow "Use soon": expires in 2-5 days
- Green "Still fresh": 6+ days

Important: `predicted_expiry` is stored and used internally; the raw date is NOT shown
in the UI. Users see "5 days" or "tomorrow," not "2026-04-03." This is the distinction
between "skip expiry date display" and "store expiry date" — they are separate concerns.

Tap any item → inline action row appears:
- "Used it" → sets `status = 'consumed'`, `status_at = now()`, row animates out
- "Edit" → modal to change name, quantity, or predicted expiry
- "Remove" → sets `status = 'discarded'`, `status_at = now()`, row animates out

Layout: quick ✓ button is always visible on the right of every row. Tapping the rest
of the row expands the inline action row (Used it / Edit / Remove) below the item.
Both are simultaneously visible — ✓ is a shortcut for "Used it" without expanding.

**3. Reminder chat screen**

Input: plain English ("remind me about fruit 2 hours after lunch").
GPT-4o parses into the `reminders` schema. Writes to SQLite.

Anchor times (`lunch_time`, `dinner_time`) are global config in the `settings` table,
set on first launch via two time pickers. Editable any time via a Settings screen
(gear icon in the nav bar). Changing them triggers an immediate notification reschedule.

Cadence pill semantics:
- **Daily**: fires every day at the computed anchor time
- **Every 2 days**: fires if `last_fired_at` is null or ≥ 48 hours ago
- **Weekly**: fires on the day-of-week the reminder was created (stored as `weekly_day`);
  user can tap the pill to change which day

**Notification architecture — two-layer approach:**

*Primary: foreground reschedule (reliable)*
Every time the app comes to foreground (`AppState` change), run the scheduling algorithm:
cancel all pending notifications, reschedule for the next 3 days with current fridge
content. 3 days × ≤10 reminders = ≤30 scheduled notifications, well under the iOS 64 cap.
This fires correctly as long as the user opens the app at least once every 3 days —
a reasonable assumption for someone actively tracking their groceries.

*Secondary: BackgroundFetch (best-effort)*
Register an Expo BackgroundFetch task that runs the same reschedule algorithm. iOS may
throttle or skip this (especially early in app lifecycle), so it is treated as a bonus,
not the primary mechanism. Static fallback message used when content is stale.

Notification message format: freshness language only. "You have strawberries (2 days)
and chicken (tomorrow) — time to plan dinner." Never raw ISO dates.

Background task failure handling: if BackgroundFetch doesn't run, previously scheduled
notifications still fire but with the static fallback body ("Check your fridge — time
to plan dinner"). Acceptable degradation for a personal tool.

What to skip in v1:
- Recipe suggestions
- Barcode scanning (receipt photo only)
- Showing raw expiry dates (use freshness language: "tomorrow", "5 days")
- Sync / multi-device
- Auth
- Cart photo parsing (too noisy, low accuracy — receipt is better)

## Data Model

### SQLite: `settings` table (global config)
```sql
CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
-- Seed rows on first launch:
-- ('lunch_time',  '12:00')
-- ('dinner_time', '18:30')
```
Anchor times are global. Changing lunch time in Settings updates this row; the
scheduler reads it fresh on every reschedule pass. No per-reminder duplication.
Settings screen (tab or gear icon) lets the user update these any time after first launch.

### SQLite: `items` table
```sql
CREATE TABLE items (
  id               TEXT PRIMARY KEY,
  name             TEXT NOT NULL,
  quantity         TEXT,               -- "1 pint", "2 lbs", "1 bag"
  purchase_date    TEXT NOT NULL,      -- ISO date: "2026-03-29"
  predicted_expiry TEXT NOT NULL,      -- ISO date: derived from LLM estimate or receipt
  status           TEXT DEFAULT 'in_fridge',
                                       -- 'in_fridge' | 'consumed' | 'discarded'
  status_at        TEXT                -- ISO datetime when status changed, null until then
);
```
`status` replaces the `consumed` integer. `'discarded'` maps to "Remove" action (thrown
out, not eaten) — distinct from `'consumed'` (eaten). Both are hidden from fridge view.
The distinction enables v2 waste tracking without a schema migration.

### SQLite: `reminders` table
```sql
CREATE TABLE reminders (
  id            TEXT PRIMARY KEY,
  title         TEXT NOT NULL,      -- "Fruit reminder"
  anchor        TEXT NOT NULL,      -- "after_lunch" | "before_dinner" | "fixed_time"
  anchor_offset INTEGER,            -- minutes relative to anchor (120 = 2h after; -60 = 1h before)
                                    -- null when anchor = "fixed_time"
  fixed_time    TEXT,               -- "07:00" HH:MM; non-null only when anchor = "fixed_time"
  cadence       TEXT NOT NULL,      -- "daily" | "every_2_days" | "weekly"
  weekly_day    INTEGER,            -- 0=Sun…6=Sat; non-null only when cadence = "weekly"
                                    -- defaults to day-of-week reminder was created
  last_fired_at TEXT,               -- ISO datetime; used to compute next "every_2_days" fire
  enabled       INTEGER DEFAULT 1
);
```

**Scheduling algorithm** (run by the scheduler on app foreground + best-effort nightly):
1. Read `lunch_time` and `dinner_time` from `settings`.
2. For each enabled reminder, compute next fire time:
   - `"after_lunch"`: today's lunch_time + anchor_offset minutes
   - `"before_dinner"`: today's dinner_time + anchor_offset minutes (offset is negative)
   - `"fixed_time"`: parse fixed_time as today's HH:MM
3. Apply cadence to determine which days to schedule across the 3-day window:
   - `"daily"`: schedule all 3 days
   - `"every_2_days"`: write `last_fired_at = now()` at schedule time (not at interaction
     time — simpler, predictable). Schedule day+2 and day+4 relative to last_fired_at.
   - `"weekly"`: schedule only the day(s) in the 3-day window that match `weekly_day`
4. If computed fire time is already past for today, start from tomorrow.
5. Cancel all pending Expo Notifications, reschedule for next 3 days (not 7 —
   keeps well under the 64-notification iOS cap even with many reminders).

**`fixed_time` anchor**: GPT-4o recognises "7am" / "every morning at 7" as
`anchor = "fixed_time"`, `fixed_time = "07:00"`, `anchor_offset = null`. The chat
prompt explicitly lists all three anchor types with examples.

**GPT-4o reminder parsing response schema:**
```json
{
  "reminders": [
    {
      "title": "Fruit reminder",
      "anchor": "after_lunch",
      "anchor_offset": 120,
      "fixed_time": null,
      "cadence": "daily"
    },
    {
      "title": "Dinner prep ideas",
      "anchor": "before_dinner",
      "anchor_offset": -60,
      "fixed_time": null,
      "cadence": "daily"
    },
    {
      "title": "Breakfast ideas",
      "anchor": "fixed_time",
      "anchor_offset": null,
      "fixed_time": "07:00",
      "cadence": "daily"
    }
  ]
}
```
`anchor_offset` is positive for "after" anchors, negative for "before" anchors.
The prompt instructs GPT-4o explicitly: "use negative minutes for 'before' reminders."

### GPT-4o vision response schema (receipt → items)
```json
{
  "items": [
    {
      "name": "Strawberries",
      "quantity": "1 pint",
      "predicted_expiry_days": 5,
      "confidence": "high"
    }
  ],
  "parse_notes": "Receipt partially obscured — 2 items may be missing"
}
```
`confidence` is `"high"` / `"medium"` / `"low"`. Low-confidence items are highlighted
in amber on the confirmation list with an edit prompt ("Tap to confirm").
`predicted_expiry_days` is relative to today; app converts to absolute ISO date.

**Image prep before API call**: resize receipt photo to max 1024px on the long edge
before base64 encoding (use `expo-image-manipulator`). Typical receipt photo goes from
~5 MB to ~200 KB. GPT-4o vision works fine at this resolution for text extraction.

**Duplicate handling**: on confirmation screen, use fuse.js to fuzzy-match each parsed
item name against existing `status = 'in_fridge'` items (threshold: score ≥ 0.8).
On match, show warning badge: "You already have Strawberries — add anyway?"
V1: user can only add as a separate row (no quantity merge — `quantity` is free text,
merging "1 pint" + "1 pint" is undefined). Just show the warning and let user decide.

### API key storage
Use `expo-secure-store` (encrypted, device-only). Never hardcode, never `AsyncStorage`.
User pastes their OpenAI API key on first launch → stored via `SecureStore.setItemAsync`.
On API 429 (rate limit): show toast "OpenAI rate limit hit — try again in a moment,"
do not retry automatically. On other API errors: show "couldn't parse — add manually"
fallback with simple text entry.

## Open Questions (resolved)

1. **Expiry prediction**: DECIDED — hybrid. GPT-4o extracts the date from receipt text
   if clearly visible (packaged goods with printed dates), estimates otherwise (produce).
   All dates shown to user for confirmation before saving. User can tap to edit.

2. **Notification content**: DECIDED — at reschedule time (foreground or BackgroundFetch),
   query SQLite for red+yellow items and build message using freshness language only:
   "You have chicken (tomorrow) and strawberries (2 days) — time to plan dinner."
   Static fallback if no fridge data available: "Check your fridge — time to plan dinner."

3. **Item consumption tracking**: DECIDED — `status` TEXT field (`'in_fridge'` /
   `'consumed'` / `'discarded'`) + `status_at` timestamp, never hard-delete. Items with
   `status != 'in_fridge'` hidden from fridge view. The `status` field (not a `consumed`
   integer) enables v2's waste/discard distinction without a schema migration.

## Success Criteria

- Takes a receipt photo at checkout, ≥80% of items parsed within 30 seconds
  (thermal paper, crumples, and lighting vary; 100% accuracy is not the goal)
- Fruit reminder fires 2 hours after lunch with what's in the fridge
- Dinner reminder fires 1 hour before dinner with what to use first
- Consumed items removed from list in one tap
- Zero manual text entry required to track a full grocery run

## Known Limitations

- **Notification reliability has a circular dependency**: the primary reschedule mechanism
  fires when the user opens the app. If the user forgets to open the app for >3 days
  (the exact failure mode this app solves), scheduled notifications expire and stop firing.
  BackgroundFetch mitigates this but is not guaranteed on iOS. Acceptable for a personal
  tool; worth noting if sharing with others.

- **Receipt quality varies**: thermal receipts fade, crumple, and vary in lighting.
  ≥80% parse accuracy is the realistic target, not 100%. The confirmation screen is the
  safety net.

- **No quantity merge on duplicates**: free-text quantity fields can't be reliably merged.
  Duplicate warning shows; user adds separately or skips.
